--- CONTENT_HTML ---
<h2 data-narration-id="n1">Why Break Code into Subprograms?</h2>
<p data-narration-id="n2">As programs grow longer, keeping everything in one flat block of code becomes unmanageable. A <dfn class="term" data-def="A named, self-contained block of code that performs a specific task and can be called by name from anywhere in the program.">subprogram</dfn> is a named block of code that does one clearly defined job. You call it by name whenever that job needs doing, rather than copying the code every time. Python supports two types of subprogram: <strong>procedures</strong> and <strong>functions</strong>. Edexcel is precise about the distinction &mdash; confusing them is one of the most penalised errors in exam answers.</p>

<div class="key-fact" data-narration-id="n3" data-revision-tip="Cover this and state the precise difference between a function and a procedure in Python — what does each one do or not do?">
  <div class="key-fact-label">Key Fact</div>
  <p>A <strong>function</strong> MUST return a value using <code>return</code>. A <strong>procedure</strong> does NOT return a value. Both may take parameters. Writing &ldquo;a function performs a task&rdquo; without mentioning the return value is an incomplete definition that loses marks.</p>
</div>

<h2 data-narration-id="n4">Procedures in Python</h2>
<p data-narration-id="n5">A <dfn class="term" data-def="A subprogram that performs a task but does not return a value to the calling code.">procedure</dfn> is defined with <code>def</code>, may take parameters, performs its task, and then simply ends. It does not hand anything back to the line that called it.</p>

<pre data-narration-id="n6">def print_greeting(name):
    print(&quot;Hello,&quot;, name, &quot;- welcome to the system!&quot;)

# Calling the procedure
print_greeting(&quot;Priya&quot;)
print_greeting(&quot;Ali&quot;)</pre>

<p data-narration-id="n7">The procedure executes, produces output, and exits. The calling code receives nothing back. Good uses for procedures: printing a menu, displaying a result, writing a line to a file, sending a notification.</p>

<h2 data-narration-id="n8">Functions in Python</h2>
<p data-narration-id="n9">A <dfn class="term" data-def="A subprogram that performs a task and returns a value to the calling code using the return statement.">function</dfn> is also defined with <code>def</code>, but it uses <code>return</code> to send a result back. The returned value replaces the function call in the expression where it appears.</p>

<pre data-narration-id="n10">def calculate_area(length, width):
    area = length * width
    return area

# Calling the function and using the returned value
room_area = calculate_area(5, 4)
print(&quot;Area:&quot;, room_area, &quot;square metres&quot;)

# The return value can also be used directly in an expression:
if calculate_area(3, 3) &gt; 8:
    print(&quot;Room is large enough&quot;)</pre>

<h2 data-narration-id="n14">Parameters</h2>
<p data-narration-id="n15"><dfn class="term" data-def="A variable listed in a subprogram definition that receives a value when the subprogram is called; the passed value is available inside the subprogram for the duration of the call.">Parameters</dfn> are the input variables listed in the subprogram&rsquo;s definition. When you call the subprogram, you pass <strong>arguments</strong> &mdash; the actual values &mdash; which are assigned to the parameter names. The order must match: the first argument goes to the first parameter, and so on.</p>

<pre data-narration-id="n16">def greet_student(first_name, year_group):
    print(&quot;Welcome, Year&quot;, year_group, &quot;student&quot;, first_name)

greet_student(&quot;Beth&quot;, 10)   # first_name = &quot;Beth&quot;, year_group = 10</pre>

<h2 data-narration-id="n17">Local and Global Variables &mdash; Scope</h2>
<p data-narration-id="n18"><dfn class="term" data-def="The part of a program where a variable can be accessed; a variable's scope is determined by where it is declared.">Scope</dfn> describes which parts of a program can read or change a variable. A <dfn class="term" data-def="A variable declared inside a subprogram that only exists while the subprogram is running and cannot be accessed from code outside it.">local variable</dfn> is declared inside a <code>def</code> block. It is created when the function is called and destroyed when it returns. Nothing outside the function can access it.</p>

<pre data-narration-id="n19">def calculate_tax(price):
    tax_rate = 0.20    # local variable
    tax = price * tax_rate
    return tax

# tax_rate and tax do NOT exist out here
print(calculate_tax(100))   # 20.0</pre>

<p data-narration-id="n20">A <dfn class="term" data-def="A variable declared outside all subprograms, accessible from any part of the program.">global variable</dfn> is declared at module level (outside all functions). It can be read anywhere in the program. To <strong>reassign</strong> it inside a function, you must use the <code>global</code> keyword; otherwise Python creates a new local variable with the same name instead.</p>

<div class="collapsible">
  <button class="collapsible-toggle" aria-expanded="false">
    <span>Why Prefer Local Variables?</span>
    <svg class="collapsible-icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><polyline points="6 9 12 15 18 9"/></svg>
  </button>
  <div class="collapsible-content"><div class="collapsible-inner">
    <p data-narration-id="n21">Local variables reduce the risk of bugs. If a global variable called <code>score</code> is shared across ten functions, any one of them could accidentally overwrite it. A bug that corrupts the score could be anywhere in the program &mdash; finding it means checking all ten functions. If <code>score</code> is instead a local parameter, only that function can change it. The problem is isolated immediately.</p>
    <p data-narration-id="n22">Use global variables only for values that genuinely need to be shared across the whole program &mdash; for example, a configuration setting loaded once at start-up, or a game&rsquo;s running total score that every function needs to update.</p>
  </div></div>
</div>

<h2 data-narration-id="n23">Built-in and Library Subprograms</h2>
<p data-narration-id="n24">Python comes with many <dfn class="term" data-def="A subprogram provided as part of the Python language itself, available without importing anything, such as print(), input(), len() and int().">built-in subprograms</dfn> that are always available: <code>print()</code>, <code>input()</code>, <code>len()</code>, <code>int()</code>, <code>float()</code>, <code>str()</code>, <code>range()</code>. These are functions &mdash; most of them return a value. Python also has an extensive standard library of <dfn class="term" data-def="A subprogram provided in a Python module that must be imported before use, such as functions from the math or random modules.">library subprograms</dfn> that must be imported before use, such as <code>import math</code> and then <code>math.sqrt(25)</code>.</p>

<h2 data-narration-id="n25">Types of Program Error</h2>
<p data-narration-id="n26">When a program fails, the error falls into one of three categories. Understanding which type of error you are dealing with determines where to look for the fix.</p>
<p data-narration-id="n27">A <dfn class="term" data-def="An error caused by code that breaks the rules of the Python language, preventing the program from running at all.">syntax error</dfn> occurs when the code violates the rules of Python. The program will not run at all. Python reports the line number and type of problem. Common causes: missing colon at the end of an <code>if</code> or <code>def</code> line, misspelled keyword, unmatched brackets.</p>
<p data-narration-id="n28">A <dfn class="term" data-def="An error that occurs while a program is running, causing it to crash; the code is syntactically valid but attempts an impossible operation.">runtime error</dfn> occurs during execution. The syntax is correct, so Python starts running the program &mdash; but something goes wrong mid-execution. Examples: dividing by zero (<code>ZeroDivisionError</code>), using an index beyond the end of a list (<code>IndexError</code>), trying to convert &ldquo;hello&rdquo; to an integer (<code>ValueError</code>).</p>
<p data-narration-id="n29">A <dfn class="term" data-def="An error where the program runs without crashing but produces incorrect results because the logic of the algorithm is flawed.">logic error</dfn> is the most difficult to find. The program runs without crashing &mdash; but it produces the wrong answer. Examples: using <code>&gt;</code> when the condition should be <code>&gt;=</code>, updating a total inside a loop but printing it inside the loop instead of after it, or initialising an accumulator to 1 instead of 0.</p>

<div class="key-fact" data-narration-id="n30" data-revision-tip="Test yourself: give one example of each error type — syntax, runtime, and logic — in Python code.">
  <div class="key-fact-label">Key Fact</div>
  <p>Syntax error: program won&rsquo;t run at all &mdash; Python language rules broken. Runtime error: program starts but crashes during execution &mdash; impossible operation attempted. Logic error: program runs to completion but produces the wrong output &mdash; the algorithm itself is flawed. Only a logic error can be invisible to Python &mdash; the other two produce explicit error messages.</p>
</div>

<h2 data-narration-id="n31">Test Data &mdash; Normal, Boundary and Erroneous</h2>
<p data-narration-id="n32">Testing requires choosing <strong>test data</strong> that exercises different parts of the program. Three categories of test data cover the essential cases for any input that must lie within a range.</p>
<p data-narration-id="n33"><dfn class="term" data-def="Test data that represents typical, expected values that the program should process correctly.">Normal test data</dfn> uses typical values well within the valid range. For an age input (0 to 120), normal data might be 25, 45, 67. <dfn class="term" data-def="Test data that uses values at the exact edges of the valid range, to verify the boundary conditions of the program are handled correctly.">Boundary test data</dfn> (also called edge data) tests the extreme limits: for the range 0&ndash;120, test 0, 1, 119, and 120. <dfn class="term" data-def="Test data that is clearly outside the valid range or of the wrong type, used to verify the program handles invalid input gracefully.">Erroneous test data</dfn> is deliberately invalid: -1, 121, or &ldquo;hello&rdquo; for an age field.</p>

--- CONCLUSION_HTML ---
<h3 data-narration-id="n38">Key Takeaways</h3>
<ul>
  <li data-narration-id="n39">A function MUST return a value using <code>return</code>. A procedure does NOT return a value. Both are defined with <code>def</code> and may take parameters.</li>
  <li data-narration-id="n40">Local variables exist only inside the subprogram where they are defined; global variables are accessible everywhere. Prefer local variables to reduce bugs and improve maintainability.</li>
  <li data-narration-id="n41">Three error types: syntax (code breaks Python rules, won't run), runtime (crashes during execution), logic (runs but produces wrong results). Test with normal, boundary and erroneous data.</li>
</ul>

--- EXAM_TIP_HTML ---
<p data-narration-id="n37">The most common mark loss in &ldquo;Write a Subprogram&rdquo; questions is a function that forgets to include <code>return</code>, or a procedure that accidentally returns a value. Always write the signature first (<code>def name(parameters):</code>), then the body, then <code>return</code> at the end if it is a function. For error-type questions, be precise: a syntax error means Python language rules are broken; a logic error means the algorithm produces wrong results but runs without crashing. &ldquo;A mistake in the code&rdquo; is too vague for marks.</p>
