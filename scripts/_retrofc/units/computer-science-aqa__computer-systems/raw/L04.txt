--- CONTENT_HTML ---
<h2 data-narration-id="n1">Hardware and Software</h2>
<p data-narration-id="n2"><dfn class="term" data-def="Physical components of a computer system that you can touch, such as the processor, memory, keyboard and monitor.">Hardware</dfn> is the physical equipment that makes up a computer. <dfn class="term" data-def="A set of instructions that tells hardware what to do. Software cannot be touched &mdash; it exists as data stored on hardware.">Software</dfn> is the set of instructions that tells the hardware what to do. Neither is useful without the other: the most powerful processor in the world does nothing without software to direct it, and the cleverest program needs hardware to run on.</p>

<div class="key-fact" data-narration-id="n3" data-revision-tip="Cover this and recall: what are the two main categories of software, and give one example of each.">
  <div class="key-fact-label">Key Fact</div>
  <p>All software falls into one of two categories: <strong>system software</strong>, which manages the computer&rsquo;s resources and provides a platform for other software to run, and <strong>application software</strong>, which performs tasks directly for the end user.</p>
</div>

<h2 data-narration-id="n4">System Software</h2>
<p data-narration-id="n5"><dfn class="term" data-def="Software that manages computer system resources and provides a platform on which application software can run. Examples include operating systems and utility programs.">System software</dfn> sits between the hardware and the user. It handles the low-level work that applications rely on. The three main types are the operating system, utility programs, and device drivers.</p>
<p data-narration-id="n6">An <dfn class="term" data-def="A type of system software that manages hardware resources and provides services for application software. Examples include Windows, macOS, iOS and Android.">operating system (OS)</dfn> manages five key areas: the <strong>processor</strong> (deciding which programs get CPU time), <strong>memory</strong> (allocating RAM to programs as they open), <strong>input/output devices</strong> (communicating with keyboards, screens, printers), <strong>applications</strong> (providing services applications need, such as file access), and <strong>security</strong> (managing user accounts and access permissions). Without the OS, every application would need to include its own code for all of these &mdash; an impossible duplication of effort.</p>
<p data-narration-id="n7">Utility programs carry out maintenance tasks. A file compression tool reduces the size of files before they are transferred; a disk cleanup tool removes temporary files to free up space; encryption software scrambles data so it cannot be read if intercepted. These are distinct from applications because they serve the system itself rather than the user&rsquo;s primary tasks.</p>

<h2 data-narration-id="n8">Application Software</h2>
<p data-narration-id="n9"><dfn class="term" data-def="Software designed to perform specific tasks for the end user, such as a word processor, web browser, or game.">Application software</dfn> is what most people think of when they think of a program: a web browser, a word processor, a banking app, a game. Applications depend entirely on system software &mdash; they request services from the OS rather than communicating with hardware directly. This separation keeps development manageable: a game developer writes code to draw a window and play sound, and the OS handles the rest.</p>

    <p data-narration-id="n10">A common exam error is to describe an antivirus program as application software. It is a utility (system software) because its purpose is to maintain the health of the system, not to help the user complete a personal task. Similarly, a device driver is system software &mdash; the user never directly interacts with it, but the OS uses it to communicate with a printer or graphics card. Application software, by contrast, is always directly task-facing: photo editing, messaging, spreadsheets.</p>

</div>

<h2 data-narration-id="n11">Programming Languages: Low-Level and High-Level</h2>
<p data-narration-id="n12">Processors can only execute instructions written in <dfn class="term" data-def="Binary instructions that can be executed directly by a processor. Each type of processor has its own specific machine code instruction set.">machine code</dfn> &mdash; patterns of 0s and 1s. Writing in machine code directly is extremely difficult and error-prone. Programming languages were developed to give programmers a more human-readable way to express instructions.</p>
<p data-narration-id="n13"><dfn class="term" data-def="Programming languages that are close to machine code, offering little or no abstraction from the hardware. Includes machine code and assembly language.">Low-level languages</dfn> are close to the hardware. They offer fine control over exactly how the processor operates, but they are difficult to read, write, and maintain. <dfn class="term" data-def="High-level languages use English-like syntax, are portable across different processors, and are much easier to read and write than low-level languages. Examples include Python and Java.">High-level languages</dfn> use English-like syntax, hide the complexity of the hardware, and can run on many different types of processor without modification.</p>

<div class="key-fact" data-narration-id="n14" data-revision-tip="Write from memory: name two differences between low-level and high-level languages.">
  <div class="key-fact-label">Key Fact</div>
  <p>High-level languages are <strong>easier to write and debug</strong>, <strong>portable</strong> across hardware, and closer to natural language. Low-level languages give <strong>precise hardware control</strong> and can produce <strong>faster, more efficient</strong> code, but they are harder to write and specific to one processor type.</p>
</div>

<h2 data-narration-id="n15">Machine Code and Assembly Language</h2>
<p data-narration-id="n16">Machine code is the only language a processor can execute directly. It is expressed entirely in binary and is specific to a processor or family of processors &mdash; code written for one architecture will not run on a different one without modification.</p>
<p data-narration-id="n17"><dfn class="term" data-def="A low-level language that uses short mnemonics (like MOV, ADD, SUB) to represent machine code instructions. It has a 1:1 correspondence with machine code: each assembly instruction maps to exactly one machine code instruction.">Assembly language</dfn> replaces raw binary with short, memorable codes called mnemonics (for example, <code>MOV</code> to move data, <code>ADD</code> to add two values). Each line of assembly corresponds to exactly one machine code instruction &mdash; this is called a <strong>1:1 correspondence</strong>. Assembly language is still tightly bound to the processor&rsquo;s architecture and is most commonly used when developing software for embedded systems or when direct control over specific hardware is needed.</p>

<h2 data-narration-id="n18">Translators: Compiler, Interpreter, Assembler</h2>
<p data-narration-id="n19">Because processors only understand machine code, any program written in a high-level or assembly language must be <em>translated</em> before it can run. There are three types of translator: the <strong>compiler</strong>, the <strong>interpreter</strong>, and the <strong>assembler</strong>.</p>

<div class="collapsible">
  <button class="collapsible-toggle" aria-expanded="false">
    <span>Compiler vs Interpreter vs Assembler &mdash; Detail</span>
    <svg class="collapsible-icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><polyline points="6 9 12 15 18 9"/></svg>
  </button>
  <div class="collapsible-content"><div class="collapsible-inner">
    <p data-narration-id="n20">A <dfn class="term" data-def="A translator that converts an entire high-level language program into machine code in one go, producing a standalone executable file.">compiler</dfn> reads the entire source code of a program and translates it all into machine code at once. The output is an executable file that can be run as many times as needed without the compiler being present. Errors are only reported after the whole program has been analysed, which makes them easier to review together. Once compiled, the program runs quickly because no further translation is needed at run time.</p>
    <p data-narration-id="n21">An <dfn class="term" data-def="A translator that converts and executes a high-level language program one line at a time, without producing a standalone executable. The interpreter must be present every time the program runs.">interpreter</dfn> translates and executes a program one line at a time. It does not produce a standalone machine code file; instead, it calls appropriate machine code subroutines within its own code to carry out each statement. If the program encounters an error mid-way, it stops at that line &mdash; making it easier to spot exactly where a mistake occurred. The downside is that the interpreter must be present every time the program runs, and execution is generally slower because translation happens at run time.</p>
    <p data-narration-id="n22">An <dfn class="term" data-def="A translator that converts assembly language into machine code. Because there is a 1:1 correspondence, each assembly instruction produces exactly one machine code instruction.">assembler</dfn> converts assembly language into machine code. Because each assembly mnemonic maps directly to one machine code instruction (the 1:1 correspondence), this translation is straightforward. Like a compiler, an assembler translates its input into machine code directly &mdash; the output is machine code that the processor can execute.</p>
    <p data-narration-id="n23">Key distinction for your exam: both assemblers and compilers translate their input <strong>directly into machine code</strong>. Interpreters do not generate machine code directly &mdash; they call machine code subroutines to carry out each statement.</p>
  </div></div>
</div>

<p data-narration-id="n24">Most modern high-level languages are typically run using an interpreter during development (easier debugging, immediate feedback) and compiled for the final product (faster execution, no dependency on the interpreter). Some languages use a combination of both approaches, compiling to an intermediate form before interpreting.</p>

--- CONCLUSION_HTML ---
<h3 data-narration-id="n26">Key Takeaways</h3>
<ul>
  <li data-narration-id="n27">System software (OS, utilities, drivers) manages hardware resources and provides a platform for applications. Application software performs end-user tasks and relies on the OS.</li>
  <li data-narration-id="n28">Low-level languages (machine code, assembly) are close to the hardware and processor-specific. High-level languages (such as Python) are portable and easier to write.</li>
  <li data-narration-id="n29">Compilers and assemblers translate source code directly into machine code; interpreters call machine code subroutines to execute programs line by line without producing a standalone executable.</li>
</ul>

--- EXAM_TIP_HTML ---
<p data-narration-id="n25">In &lsquo;compare and contrast&rsquo; questions on compilers and interpreters, make sure you address both speed and error-reporting in a single structured paragraph rather than listing features of each separately. A common error is to say interpreters &ldquo;produce machine code line by line&rdquo; &mdash; they do not produce machine code at all; they call machine code subroutines. Also remember that assemblers and compilers both translate directly to machine code, while interpreters work differently. When explaining system vs application software, always link to function: system software <em>manages resources</em>, application software <em>performs user tasks</em>.</p>
