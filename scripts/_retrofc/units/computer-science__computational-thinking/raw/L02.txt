--- DESCRIPTION ---
Turn a problem into a plan using structure diagrams, pseudocode, flowcharts and trace tables.

--- CONTENT_HTML ---
<p data-narration-id="n1">Before a programmer writes any code, they design an <dfn class="term" data-def="A precise set of step-by-step instructions for solving a problem or completing a task.">algorithm</dfn>. An algorithm is a precise set of step-by-step instructions for solving a problem or completing a task. Planning the algorithm first &mdash; on paper or on screen &mdash; means you can spot mistakes in the logic before you spend time typing real program code. This lesson looks at four tools for designing algorithms: working out the inputs and outputs, drawing structure diagrams, and writing the steps as pseudocode or as a flowchart.</p><h3 data-narration-id="n2">Inputs, processes and outputs</h3><p data-narration-id="n3">A good first step is to ask three questions: what information does the program need, what must it do with that information, and what should it produce? These are the inputs, the processes and the outputs. Take a program that works out the area of a rectangle. The inputs are the length and the width. The process is multiplying the length by the width. The output is the area, shown on the screen. Splitting a problem this way makes the design far clearer before you start coding.</p><div class="key-fact" data-narration-id="n4" data-revision-tip="Cover this and write down the inputs, process and output for a program that converts pounds into euros."><div class="key-fact-label">Key Fact</div><p>Every program can be described by its inputs (the data going in), its processes (the steps that transform the data) and its outputs (the results that come out). Working these out first is the foundation of a good algorithm.</p></div><h3 data-narration-id="n5">Breaking a problem down</h3><p data-narration-id="n6">Large problems are much easier to solve when they are split into smaller parts. This is called <dfn class="term" data-def="Breaking a large problem down into smaller, more manageable sub-problems.">decomposition</dfn>. A <dfn class="term" data-def="A diagram that shows a problem broken into sub-tasks arranged in a top-down hierarchy.">structure diagram</dfn> shows this breakdown as a hierarchy: the whole problem sits in a box at the top, and the sub-tasks branch out beneath it, with the smallest jobs at the bottom. Reading from top to bottom takes you from the general goal down to the specific tasks the program must carry out.</p><div class="collapsible"><button class="collapsible-toggle" aria-expanded="false"><span>Worked example: a quiz game structure diagram</span><svg class="collapsible-icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><polyline points="6 9 12 15 18 9"/></svg></button><div class="collapsible-content"><div class="collapsible-inner"><p data-narration-id="n7">Imagine building a quiz game. At the top is the whole task, &lsquo;Run quiz game&rsquo;. This breaks into three sub-tasks: &lsquo;Ask questions&rsquo;, &lsquo;Keep score&rsquo; and &lsquo;Show result&rsquo;. &lsquo;Ask questions&rsquo; then breaks down further into &lsquo;Display question&rsquo;, &lsquo;Get answer&rsquo; and &lsquo;Check answer&rsquo;. Each of these small boxes is now simple enough to turn straight into code.</p><pre data-narration-id="n8">Run quiz game
    Ask questions
        Display question
        Get answer
        Check answer
    Keep score
    Show result</pre></div></div></div><h3 data-narration-id="n9">Writing pseudocode</h3><p data-narration-id="n10"><dfn class="term" data-def="An algorithm written in short, code-like English that does not follow the strict syntax rules of a real language.">Pseudocode</dfn> is a way of writing an algorithm using short, code-like English. It is not a real programming language, so it does not have to follow exact syntax rules &mdash; but it does use common keywords so the logic is clear and could be turned into real code in any language. Pseudocode is quick to write and easy to read, which makes it ideal for planning.</p><pre data-narration-id="n11">score = input("Enter your score")
score = int(score)
if score &gt;= 70 then
    print("Grade: Pass with merit")
elseif score &gt;= 50 then
    print("Grade: Pass")
else
    print("Grade: Try again")
endif</pre><p data-narration-id="n12">This short algorithm shows the three building blocks that every algorithm is made from. <dfn class="term" data-def="The construct in which program steps are carried out one after another, in order.">Sequence</dfn> means the steps run one after another, in order. <dfn class="term" data-def="The construct in which a program chooses between different paths using a condition.">Selection</dfn> means the program chooses between different paths using a condition, such as the <code>if &hellip; then &hellip; else</code> above. <dfn class="term" data-def="The construct in which a set of steps is repeated using a loop.">Iteration</dfn> means repeating a set of steps, using loops such as <code>for</code> or <code>while</code>.</p><div class="collapsible"><button class="collapsible-toggle" aria-expanded="false"><span>Common pseudocode keywords</span><svg class="collapsible-icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><polyline points="6 9 12 15 18 9"/></svg></button><div class="collapsible-content"><div class="collapsible-inner"><p data-narration-id="n13">Assignment gives a value to a variable, written as <code>total = 0</code>. Input and output are usually written as <code>input</code> and <code>print</code>. Selection uses <code>if</code>, <code>then</code>, <code>elseif</code>, <code>else</code> and <code>endif</code>. Iteration uses a count-controlled loop, <code>for i = 1 to 10 &hellip; next i</code>, or a condition-controlled loop, <code>while &hellip; endwhile</code>. A <dfn class="term" data-def="A named store that holds a value which can change while a program runs.">variable</dfn> is a named store that holds a value which can change while the program runs.</p></div></div></div><div class="key-fact" data-narration-id="n14" data-revision-tip="Close this and name the three programming constructs, giving one keyword for each."><div class="key-fact-label">Key Fact</div><p>Algorithms are built from just three constructs: sequence (steps in order), selection (choosing a path with a condition) and iteration (repeating steps in a loop). Every program, however complex, is made from these three.</p></div><h3 data-narration-id="n15">Drawing flowcharts</h3><p data-narration-id="n16">A <dfn class="term" data-def="A diagram that represents an algorithm as labelled boxes joined by arrows showing the order of steps.">flowchart</dfn> is a diagram that shows an algorithm as a series of boxes joined by arrows. The shape of each box tells you what kind of step it is, and the arrows show the order the steps run in. Flowcharts are especially good at showing decisions and loops clearly.</p><p data-narration-id="n17">Each flowchart is built from a standard set of symbols:</p><ul><li data-narration-id="n18"><strong>Terminal</strong> &mdash; a rounded box that marks the start or the stop of the algorithm.</li><li data-narration-id="n19"><strong>Process</strong> &mdash; a rectangle for an action or a calculation, such as adding one to a score.</li><li data-narration-id="n20"><strong>Input/output</strong> &mdash; a parallelogram (a slanted box) for data going in or results coming out.</li><li data-narration-id="n21"><strong>Decision</strong> &mdash; a diamond holding a yes/no or true/false question, with a branch leaving each answer.</li><li data-narration-id="n22"><strong>Sub program</strong> &mdash; a rectangle with double side lines that calls a separate, named routine.</li><li data-narration-id="n23"><strong>Flow line</strong> &mdash; an arrow that connects the symbols and shows the direction of flow.</li></ul><p data-narration-id="n24">The real power of a flowchart comes from the decision symbol. A loop is drawn by sending one branch of a decision back to an earlier point, so the steps repeat until the condition is met. Following the arrows from the start terminal to the stop terminal traces the whole algorithm.</p><div class="collapsible"><button class="collapsible-toggle" aria-expanded="false"><span>Worked example: a login check flowchart</span><svg class="collapsible-icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><polyline points="6 9 12 15 18 9"/></svg></button><div class="collapsible-content"><div class="collapsible-inner"><p data-narration-id="n25">A login check starts at a terminal marked &lsquo;Start&rsquo;. An input/output symbol asks the user to enter a password. A decision symbol then asks &lsquo;Is the password correct?&rsquo;. If the answer is yes, a process grants access and the flow reaches the stop terminal. If the answer is no, the flow line loops back to the input symbol so the user can try again.</p></div></div></div><h3 data-narration-id="n26">Checking an algorithm with a trace table</h3><p data-narration-id="n27">Once an algorithm is designed, you can check it works using a <dfn class="term" data-def="A grid used to record how the variables in an algorithm change, in order to check its logic.">trace table</dfn>. This is a grid with a column for each variable and each output. You work through the algorithm by hand, one step at a time, writing down how the values change. Trace tables are the best way to find logic errors, especially inside loops, because they show exactly what the program would do.</p><div class="collapsible"><button class="collapsible-toggle" aria-expanded="false"><span>Reading a trace table</span><svg class="collapsible-icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><polyline points="6 9 12 15 18 9"/></svg></button><div class="collapsible-content"><div class="collapsible-inner"><p data-narration-id="n28">Suppose a loop starts with <code>total = 0</code> and adds the numbers 3, then 5, then 2. A trace table records the value of <code>total</code> after each pass through the loop: it starts at 0, becomes 3, then 8, then 10. If the final total is not what you expected, the table shows you the exact step where the logic went wrong.</p><table data-narration-id="n29"><thead><tr><th>Step</th><th>number</th><th>total</th></tr></thead><tbody><tr><td>Start</td><td>&mdash;</td><td>0</td></tr><tr><td>Pass 1</td><td>3</td><td>3</td></tr><tr><td>Pass 2</td><td>5</td><td>8</td></tr><tr><td>Pass 3</td><td>2</td><td>10</td></tr></tbody></table></div></div></div><h3 data-narration-id="n30">Pseudocode or flowchart?</h3><p data-narration-id="n31">Both tools describe the same algorithm, so which you choose is often up to you. Pseudocode is fast to write and translates easily into real code, so programmers often prefer it for longer designs. Flowcharts are more visual and make branching and loops easy to see at a glance, which helps when explaining an idea to someone else. A skilled designer can move comfortably between the two.</p>

--- CONCLUSION_HTML ---
<h3 data-narration-id="n33">Key Takeaways</h3><ul><li data-narration-id="n34">Design an algorithm before coding: identify the inputs, processes and outputs, then break the problem down with a structure diagram.</li><li data-narration-id="n35">Pseudocode and flowcharts both describe an algorithm using the three constructs of sequence, selection and iteration.</li><li data-narration-id="n36">A trace table checks an algorithm by recording how each variable changes, step by step, which reveals logic errors.</li></ul>

--- EXAM_TIP_HTML ---
<p data-narration-id="n32">When a question asks you to &lsquo;complete&rsquo; or &lsquo;refine&rsquo; an algorithm, read the existing lines carefully first &mdash; your answer must fit the style already used. If you are asked to &lsquo;write&rsquo; an algorithm you may use pseudocode or a flowchart unless the question names one, but keep your steps in a clear order and label your inputs and outputs. For a &lsquo;trace table&rsquo; question, fill in one row per step and never skip a loop pass, because the marks are given for showing every change to the values.</p>
