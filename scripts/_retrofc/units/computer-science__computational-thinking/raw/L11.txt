--- DESCRIPTION ---
How high-level and low-level languages, compilers, interpreters and IDEs turn code into software.

--- CONTENT_HTML ---
<p data-narration-id="n1">Computers ultimately understand only one thing: patterns of binary 1s and 0s. Yet almost nobody writes programs directly in binary &mdash; it would be painfully slow and terribly easy to get wrong. Instead, programmers pick a language that suits the job and rely on other software to turn their code into something the processor can actually run. This lesson looks at the different levels of programming language, the translators that convert your code, and the toolkit that makes writing software far quicker.</p>

<h3 data-narration-id="n2">High-level and low-level languages</h3>

<p data-narration-id="n3">Programming languages sit on a scale, depending on how close they are to human language or to the raw instructions of the processor. A <dfn class="term" data-def="A programming language that uses English-like keywords, is easy for people to read and write, and must be translated before a computer can run it.">high-level language</dfn> such as Python, Java or C++ is written using English-like keywords such as &lsquo;if&rsquo;, &lsquo;print&rsquo; and &lsquo;while&rsquo;. A single line of high-level code usually stands in for many processor instructions. This makes high-level code easier to read, write and debug, and it is portable &mdash; the same program can run on different types of computer once it has been translated. Its one catch is that it must always be translated before the processor can understand it.</p>

<p data-narration-id="n4">A <dfn class="term" data-def="A programming language that is close to the hardware, such as machine code, which is fast and machine-specific but hard for people to read and write.">low-level language</dfn> is much closer to the hardware. The lowest level is <dfn class="term" data-def="Binary instructions that a processor can execute directly, without any translation.">machine code</dfn> &mdash; pure binary that the processor runs directly, with no translation needed. Assembly language is also low-level, replacing binary with short memory-joggers called mnemonics. Low-level code is hard for people to read and write, and it is machine-specific, so it only works on one type of processor. In return it runs very fast, uses little memory and gives the programmer precise control over the hardware, which is why it is used for tasks like device drivers and other software that must squeeze the most out of the machine.</p>

<div class="key-fact" data-narration-id="n5" data-revision-tip="Cover this and list two advantages of a high-level language and two advantages of a low-level language.">
  <div class="key-fact-label">Key Fact</div>
  <p>High-level languages use English-like keywords, are easy to read and debug, and are portable across different machines. Low-level languages are close to the hardware: harder to write and machine-specific, but faster and more memory-efficient.</p>
</div>

For most everyday software, that productivity and portability easily outweigh the small loss of speed.</p>

<h3 data-narration-id="n7">Translators: compilers and interpreters</h3>

<p data-narration-id="n8">Because a processor can only run machine code, any program written in a high-level language has to be converted first. A <dfn class="term" data-def="A program that converts source code into machine code so that the processor can run it.">translator</dfn> is a program that turns <dfn class="term" data-def="The code a programmer writes in a programming language, before it is translated into machine code.">source code</dfn> &mdash; the code a programmer writes &mdash; into machine code. The two translators you need to know are the compiler and the interpreter. They do the same job in very different ways.</p>

<p data-narration-id="n9">A <dfn class="term" data-def="A translator that converts the whole program into machine code in one go, producing an executable file that can be run on its own.">compiler</dfn> translates the entire program in one go, before it is run. It produces a separate <dfn class="term" data-def="A ready-to-run file of machine code produced by a compiler, which runs without needing the source code or the translator.">executable file</dfn> of machine code that can then be run on its own, without the source code or the compiler being present. Compiling a large program can take a while, but the finished executable then runs quickly. A compiler checks the whole program and produces an error report at the end, listing the mistakes together rather than stopping at the first one.</p>

<p data-narration-id="n10">An <dfn class="term" data-def="A translator that converts and runs a program one statement at a time, needing the source code and interpreter present every time.">interpreter</dfn> translates and runs the program one statement at a time. It does not create an executable file, so the interpreter and the source code are both needed every time the program runs. Because it translates as it goes, an interpreted program runs more slowly. However, the interpreter stops at the very first error it meets and reports it straight away, which makes mistakes much easier to find and fix while a program is still being developed.</p>

<div class="key-fact" data-narration-id="n11" data-revision-tip="Close this and write one benefit and one drawback of a compiler, then do the same for an interpreter.">
  <div class="key-fact-label">Key Fact</div>
  <p>A compiler translates the whole program at once into a fast, standalone executable, but reports all its errors together at the end. An interpreter translates line by line, runs more slowly and needs the source code each time, but stops at the first error, making debugging easier.</p>
</div>

<div class="collapsible">
  <button class="collapsible-toggle" aria-expanded="false">

    <svg class="collapsible-icon" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2"><polyline points="6 9 12 15 18 9"/></svg>
  </button>
  <div class="collapsible-content"><div class="collapsible-inner">
    <p data-narration-id="n12">A compiler is a good choice for finished software you want to share. The executable runs fast, works without the original source code, and keeps that source code hidden from users. The drawbacks are that you must recompile the whole program after every change, and the executable only runs on the type of processor it was built for.</p>
    <p data-narration-id="n13">An interpreter suits writing and testing programs. Errors are caught one at a time, and the same source code will run on any device that has the right interpreter, which makes it very portable. The trade-offs are slower running speed and the fact that the source code must be handed over to anyone who wants to run the program.</p>

</div>

<h3 data-narration-id="n14">Integrated Development Environments</h3>

<p data-narration-id="n15">Writing, running and fixing code in separate programs would be slow, so programmers use an <dfn class="term" data-def="A single application that brings together the tools a programmer needs to write, run and debug programs.">Integrated Development Environment</dfn>, or IDE &mdash; a single application that brings all the tools they need into one place. Popular examples include IDLE for Python, PyCharm and Visual Studio. An IDE usually provides four kinds of tool.</p>

<ul>
  <li data-narration-id="n16"><strong>Editor</strong> &mdash; where you type your code. Helpful features such as colour-coded keywords (syntax highlighting), automatic indentation, auto-complete and line numbering make code faster to write and easier to read.</li>
  <li data-narration-id="n17"><strong>Error diagnostics</strong> &mdash; tools that help track down mistakes. A <dfn class="term" data-def="A marker that pauses a running program at a chosen line so the programmer can inspect it.">breakpoint</dfn> pauses the program at a chosen line, and the programmer can then step through the code line by line and watch how the values stored in variables change, pinpointing where a fault happens.</li>
  <li data-narration-id="n18"><strong>Run-time environment</strong> &mdash; a <dfn class="term" data-def="The part of an IDE that lets a programmer run a program and see its output without needing separate software.">run-time environment</dfn> lets the programmer run the program from inside the IDE and see its output straight away.</li>
  <li data-narration-id="n19"><strong>Translator</strong> &mdash; a built-in compiler or interpreter that converts the code into machine code so it can actually run.</li>
</ul>

<p data-narration-id="n20">Because all of these tools sit in one window, an IDE speeds up the whole write, run and debug cycle. That is why almost all software today is created using one.</p>

--- CONCLUSION_HTML ---
<h3 data-narration-id="n22">Key Takeaways</h3>
<ul>
  <li data-narration-id="n23">High-level languages are written in English-like keywords and are portable and easy to debug; low-level languages sit close to the hardware and are fast but machine-specific.</li>
  <li data-narration-id="n24">A compiler translates the whole program at once into a standalone executable, while an interpreter translates and runs it line by line, stopping at the first error.</li>
  <li data-narration-id="n25">An IDE combines an editor, error-diagnostic tools, a run-time environment and a translator so that code can be written, run and fixed in one place.</li>
</ul>

--- EXAM_TIP_HTML ---
<p data-narration-id="n21">Watch the command word carefully. &lsquo;State&rsquo; or &lsquo;Give&rsquo; wants a quick fact with no explanation, while &lsquo;Describe&rsquo; and especially &lsquo;Explain&rsquo; expect you to say how or why. A very common question asks you to compare a compiler and an interpreter &mdash; make sure each point is a genuine contrast (for example, &lsquo;a compiler translates all the code at once, whereas an interpreter translates one line at a time&rsquo;) rather than two facts that never mention each other. When a question is about an IDE, name a specific tool and then say exactly how it helps the programmer, not just what it is.</p>
