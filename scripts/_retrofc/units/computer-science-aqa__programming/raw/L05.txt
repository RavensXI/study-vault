--- CONTENT_HTML ---
<h2 data-narration-id="n1">What Is Robust Programming?</h2>
<p data-narration-id="n2">A <dfn class="term" data-def="A program that handles unexpected or invalid inputs without crashing, by checking data before processing it and verifying user identity where needed.">robust program</dfn> does not crash when something goes wrong. Users make mistakes &mdash; they enter text where a number is expected, leave fields blank, or type a value that is out of range. A robust program anticipates these problems and deals with them gracefully. Writing robust code means building in three things: <strong>data validation</strong>, <strong>authentication</strong>, and <strong>testing</strong>.</p>

<h2 data-narration-id="n3">Data Validation</h2>
<p data-narration-id="n4"><dfn class="term" data-def="Checking that data entered by a user meets specified criteria before the program processes it. Validation checks if data is reasonable, not whether it is correct.">Data validation</dfn> checks that input data is sensible and within the expected rules before the program uses it. Validation does <em>not</em> guarantee the data is accurate or true &mdash; it only confirms it meets the required format or range. For example, a date of birth field can be validated to ensure the year is between 1900 and 2025, but validation cannot check whether that is your <em>real</em> date of birth.</p>
<p data-narration-id="n5">The specification identifies three specific validation checks you need to be able to write:</p>
<ul>
  <li data-narration-id="n6"><strong>Minimum length check</strong> &mdash; confirms the entered string has at least a required number of characters. For example, a username might need at least three characters.</li>
  <li data-narration-id="n7"><strong>Empty string check (presence check)</strong> &mdash; confirms the user has entered something at all rather than leaving the field blank.</li>
  <li data-narration-id="n8"><strong>Range check</strong> &mdash; confirms that a number falls within an acceptable range, for example between 1 and 10.</li>
</ul>

    <pre data-narration-id="n10">SUBROUTINE getValidScore()
   REPEAT
      score &larr; INPUT("Enter a score (1&ndash;10): ")

   UNTIL score &gt;= 1 AND score &lt;= 10
   RETURN score
ENDSUBROUTINE</pre>

   REPEAT
      username &larr; INPUT("Enter username (min 3 chars): ")
   UNTIL LEN(username) &gt;= 3
   RETURN username
ENDSUBROUTINE</pre>

  <div class="key-fact-label">Key Fact</div>
  <p>The three validation checks required by the specification are: <strong>minimum length</strong> (LEN check), <strong>empty string</strong> (presence check), and <strong>range check</strong> (value between two bounds). Validation ensures data is <em>reasonable</em> &mdash; not necessarily <em>correct</em>.</p>
</div>

<h2 data-narration-id="n14">Authentication Routines</h2>
<p data-narration-id="n15"><dfn class="term" data-def="A routine that verifies a user&rsquo;s identity, typically by checking a username and password against stored values before granting access.">Authentication</dfn> is the process of confirming that a user is who they claim to be. You need to be able to write a simple authentication routine that checks a username and password. In exam questions, passwords are stored as plain text &mdash; you are not expected to encrypt them.</p>
<p data-narration-id="n16">A simple authentication routine compares the username and password entered by the user with stored values. If both match, access is granted. Most real systems also limit the number of attempts to prevent someone trying thousands of combinations, but even a simple three-attempt limit is good practice and may appear in exam questions.</p>

    <p data-narration-id="n17">This routine allows three attempts before locking out the user:</p>
    <pre data-narration-id="n18">storedUser &larr; "admin"
storedPass &larr; "pass123"
attempts &larr; 0
access &larr; FALSE

REPEAT
   user &larr; INPUT("Username: ")
   pass &larr; INPUT("Password: ")
   attempts &larr; attempts + 1
   IF user = storedUser AND pass = storedPass THEN
      access &larr; TRUE
   ENDIF
UNTIL access = TRUE OR attempts = 3

IF access THEN
   OUTPUT "Access granted"
ELSE
   OUTPUT "Account locked"
ENDIF</pre>

<h2 data-narration-id="n19">Testing: Types of Test Data</h2>
<p data-narration-id="n20">Testing checks that a program behaves correctly for all possible inputs, not just the obvious cases. You must be able to describe and select three types of <dfn class="term" data-def="Values used to test a program, chosen to check correct behaviour under normal conditions, at boundary points, and with invalid inputs.">test data</dfn>:</p>
<ul>
  <li data-narration-id="n21"><strong>Normal (typical) data</strong> &mdash; values that are well within the valid range. They should be accepted and processed correctly. For a range of 1&ndash;10, normal data might be 5 or 7.</li>
  <li data-narration-id="n22"><strong>Boundary (extreme) data</strong> &mdash; values at the very edge of the valid range, <em>and just outside it</em>. For a range of 1&ndash;10, boundary data is <strong>0, 1, 10 and 11</strong> &mdash; both sides of each boundary. Boundary data catches off-by-one errors that are easy to introduce when writing conditions.</li>
  <li data-narration-id="n23"><strong>Erroneous data</strong> &mdash; values that are completely outside the expected range or of the wrong type altogether. For a number field, entering the word &ldquo;banana&rdquo; or a negative number like &minus;5 is erroneous data. The program should reject this without crashing.</li>
</ul>

<div class="key-fact" data-narration-id="n24" data-revision-tip="Test yourself: for a valid age range of 0 to 120, state one example of normal, two examples of boundary and one example of erroneous test data.">
  <div class="key-fact-label">Key Fact</div>
  <p>Boundary data is <strong>both sides of each limit</strong>. For the range 1&ndash;10, the boundary values are 0, 1, 10 and 11. A common mistake is to give only one boundary value &mdash; you need all four to test both bounds fully.</p>
</div>

<h2 data-narration-id="n25">Types of Error</h2>
<p data-narration-id="n26">When a program does not work as expected, the fault is usually one of two types. A <dfn class="term" data-def="An error in the grammar or spelling of the programming language, which prevents the program from running.">syntax error</dfn> breaks the rules of the programming language &mdash; a missing bracket, a misspelled keyword, or incorrect indentation. The program will not run at all until syntax errors are fixed. A <dfn class="term" data-def="An error where the program runs without crashing but produces incorrect results because the logic of the code is wrong.">logic error</dfn> allows the program to run but produces wrong results. For example, using &ldquo;&gt;&rdquo; instead of &ldquo;&gt;=&rdquo; in a boundary check, or calculating the average by dividing by the wrong value.</p>
<p data-narration-id="n27">Logic errors are harder to find than syntax errors because the program does not tell you something is wrong &mdash; it just silently gives the wrong answer. Careful testing with all three types of test data is the best way to expose logic errors before a program is released.</p>

--- CONCLUSION_HTML ---
<h3 data-narration-id="n29">Key Takeaways</h3>
<ul>
  <li data-narration-id="n30">Robust programs use data validation (minimum length, empty string, range check) to reject bad input before processing it, and authentication (username + password check) to verify user identity.</li>
  <li data-narration-id="n31">Test data comes in three types: normal (within range), boundary (both sides of each limit &mdash; for range 1&ndash;10 that means 0, 1, 10, 11), and erroneous (completely invalid).</li>
  <li data-narration-id="n32">Syntax errors stop a program running; logic errors let it run but produce wrong results. Systematic testing with all three data types is how you find logic errors before users do.</li>
</ul>

--- EXAM_TIP_HTML ---
<p data-narration-id="n28">For questions asking you to &ldquo;select suitable test data&rdquo;, always provide all four boundary values for a range question (both sides of both limits). Writing only &ldquo;10&rdquo; for a 1&ndash;10 range loses marks. For &ldquo;Write a validation routine&rdquo; questions, use REPEAT&ndash;UNTIL so the program keeps asking until valid data is entered &mdash; examiners expect a loop, not a single check. Remember: validation checks data is <em>reasonable</em>, not correct. For authentication, you only need plain text username and password comparison &mdash; do not attempt to add hashing or encryption.</p>
